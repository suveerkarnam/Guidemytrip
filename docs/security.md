# Security

The baseline enables Helmet, restricted CORS, JSON request limits, rate limiting, compression, structured request logging, and centralized safe error responses. Secrets belong in environment variables and must never be committed. Authentication, authorization, payment verification, webhook validation, audit logs, and PII controls are required before production.

Razorpay credentials and the webhook secret are environment-only. Order amounts are recalculated from the persisted package snapshot/current catalog before an order is created. Payment signatures are checked with HMAC, webhook bodies are verified as raw bytes, and provider events are deduplicated before persistence. Frontend checkout callbacks never confirm bookings directly.

Public contact input is validated server-side and notification content is generated by the API. Public review responses filter on approved moderation status; moderation actions never change rating values.

## Phase 4 authentication controls

- Mobile numbers are normalized to E.164-like format, OTPs are HMAC-hashed, expire after a configurable window, are capped by attempts, and have a resend cooldown plus endpoint rate limit. OTP values are never returned or logged.
- The mock SMS provider is selected only for non-production development and stores delivery data only in process memory for tests. Production configuration rejects the mock provider and default development secrets.
- Access tokens are short-lived signed JWTs in HttpOnly cookies. Refresh tokens are opaque, hashed in `Session`, rotated on every refresh, revoked on logout, and rejected on reuse/expiry.
- Auth mutations require a double-submit CSRF token. Cookies use `Secure` in production and `SameSite=Lax`.
- Google identity tokens are verified by the backend with Google’s OAuth client; verified provider subjects are unique, and email matches alone never auto-link accounts.
- `requireAuth`, `requireRoles`, and `requireOwnership` middleware provide server-side authorization boundaries. Frontend guards are convenience only.
- Pino HTTP request logs redact cookies, authorization headers, and response `Set-Cookie` headers. Application errors are logged without raw request bodies or token values.
- Authentication mutations and public contact requests have dedicated rate limits in addition to the global API limit.
- Admin guide/review/contact mutations create `AuditLog` records; review moderation changes status only and cannot rewrite ratings.

## Phase 9 audit results

- Critical booking capture race fixed with a PostgreSQL transaction-scoped advisory lock and in-transaction payment/hold recheck.
- Payment signatures, webhook signatures, hold expiry, and late-payment refund handling remain server-controlled.
- Prisma parameterization is used for database access; the only raw SQL is a parameterized advisory-lock statement.
- No access/refresh tokens, OTPs, passwords, payment secrets, or card data are logged or persisted in frontend storage.
- Remaining operational limitations: online `npm audit` requires registry network access, Docker is unavailable in this environment, and Playwright/live-provider E2E tests are not yet installed.
